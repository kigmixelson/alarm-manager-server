# Образы Docker: просмотр и очистка

Инструкция для закрытого контура: как увидеть ранее загруженные комплекты
Alarm Manager и как удалить старые, не затронув работающие контейнеры и тома
с тикетами.

Образы появляются на узле после `docker load --input image.tar`. Docker Hub
и `docker pull` для этой поставки не используются.

## 1. Какой образ сейчас запущен

Тег задаётся в рабочем `.env`:

```bash
cd /opt/alarm-manager-server
grep '^ALARM_MANAGER_IMAGE=' .env
docker compose -f compose.yml ps
docker compose -f compose.yml images
```

Ожидается одно имя вида `alarm-manager-server:<тег>` и два контейнера:
`server` и `worker`. Если тег в `.env` не совпадает с загруженным образом,
Compose не стартует: `pull_policy: never` запрещает скачивание.

Какой образ держит контейнер:

```bash
docker inspect --format '{{.Name}} {{.Config.Image}} {{.Image}}' \
  $(docker compose -f compose.yml ps -q)
```

## 2. Какие образы уже загружены

Все локальные образы:

```bash
docker images
```

Только поставка Alarm Manager:

```bash
docker images alarm-manager-server
```

С размером и датой загрузки удобнее так:

```bash
docker images --format 'table {{.Repository}}\t{{.Tag}}\t{{.ID}}\t{{.CreatedSince}}\t{{.Size}}' \
  alarm-manager-server
```

Несколько тегов после обновлений — это нормально: `docker load` не удаляет
предыдущий комплект. Старый тег нужен для отката, пока новый не принят.

Образы без тега (`<none>`) — обычно остатки после перезаписи того же имени.
Их можно смотреть отдельно:

```bash
docker images --filter dangling=true
```

`image.tar` на диске (`/opt/alarm-manager-server/image.tar` или архив комплекта)
— это файл поставки, не то же самое, что запись в хранилище Docker. Удаление
файла образ из `docker images` не убирает; удаление образа файл на диске
не трогает.

## 3. Что нельзя удалять

- Образ из текущего `ALARM_MANAGER_IMAGE`, пока контейнеры на нём работают
  или пока не подтверждён новый тег.
- Предыдущий принятый тег, пока не решили, что откат больше не нужен.
- Тома Compose: `docker compose down -v` уничтожит `tickets.json` и кеш.

Проверка, что образ не занят контейнером (в том числе остановленным):

```bash
docker ps -a --filter ancestor=alarm-manager-server:СТАРЫЙ_ТЕГ
```

Пустой список — контейнеры этот тег не используют. Тогда его можно удалять.

## 4. Очистка старых тегов

Когда новый комплект уже загружен, `.env` указывает на новый тег, сервисы
пересозданы и приёмка прошла:

```bash
docker compose -f compose.yml up -d --no-build --pull never --force-recreate
docker compose -f compose.yml ps
curl --fail http://127.0.0.1:4800/health
```

Удалите только конкретный старый тег:

```bash
docker rmi alarm-manager-server:СТАРЫЙ_ТЕГ
```

Пример: после перехода на `alarm-manager-server:2026.09.30-1` можно убрать
`alarm-manager-server:2026.09.16-thick-1`, если откат на него больше не планируется.

Если Docker отвечает, что образ используется, сначала остановите и удалите
контейнеры **этого** тега или переключите их на новый. Не используйте
`docker rmi -f` в контуре: принудительное удаление занятого образа оставляет
контейнеры в несогласованном состоянии.

Только висячие слои без тега (после нескольких `docker load` с тем же именем):

```bash
docker image prune
```

Команда спросит подтверждение и не удаляет образы с тегом. Не запускайте
`docker image prune -a`: она снимет все неиспользуемые образы на узле, включая
чужие приложения и теги, оставленные для отката Alarm Manager.

Сборка на машине с интернетом плодит промежуточные слои. Их можно чистить
там же, не в закрытом контуре:

```bash
docker builder prune
```

## 5. Типичный порядок после обновления

1. Загрузить новый `image.tar` (`docker load`).
2. Убедиться, что в `docker images alarm-manager-server` есть и старый, и новый тег.
3. Прописать новый тег в `.env`, пересоздать контейнеры.
4. Проверить `/health` и логи worker (`Oracle ServiceDesk: отправка подтверждена` при тестовой аварии).
5. Подержать старый тег до конца приёмки.
6. Удалить старый тег командой `docker rmi alarm-manager-server:СТАРЫЙ_ТЕГ`.

Откат: вернуть прежний `ALARM_MANAGER_IMAGE` в `.env` и снова
`docker compose -f compose.yml up -d --no-build --pull never --force-recreate`.
Это возможно, только пока старый образ ещё есть в `docker images`.

Состояние тикетов при смене образа не трогайте: оно в томе worker, не внутри
образа. Подробности обновления — в [установке в закрытом контуре](offline-install.md#5-обновление-резервное-копирование-восстановление).
