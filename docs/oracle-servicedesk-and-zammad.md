# Oracle ServiceDesk и Zammad

Заметка для администраторов: как worker передаёт локальные тикеты во внешние
системы. Плагины подключаются автоматически, если в `.env` заполнены обязательные
параметры. Одновременно можно включить несколько интеграций.

## 1. Oracle: хендлеры кастомного корпоративного ServiceDesk

Корпоративный ServiceDesk принимает заявки не через REST, а через хранимую
функцию Oracle `REPAIR.REP_MONIT_SYSTEM_CURS`. Worker вызывает её через
`callfunc` как PL/SQL-функцию, возвращающую `SYS_REFCURSOR` (не `SELECT ... FROM dual`),
и считает заявку созданной только после успешного `commit`.

Связанные модули:

| Модуль | Назначение |
|---|---|
| `OracleTicketHandler` | Основной хендлер: запись заявки по событию `created` или `closed` |
| `oracle_diagnostics` | Ограниченная диагностика DNS/TCP при сбое подключения; SQL и повторную авторизацию не выполняет |
| `oracle_check` | Ручная проверка логина (`SELECT 1 FROM dual`) без вызова функции тикета |

Плагин включается, когда заданы DSN, логин, пароль и все четыре идентификатора:
`ORACLE_ID_DEPT`, `ORACLE_ID_BUILD`, `ORACLE_ID_DEF`, `ORACLE_ID_MONIT`.

В вызов функции параметр `P_ID_MONIT` передаётся как **номер тикета**, а не
фиксированная константа из `.env`: сначала номер заявки Oracle (если уже есть
в `external_ref` / `external_refs.oracle`), иначе числовая часть локального
тикета (`T-000012` → `12`), и только если оба недоступны — `ORACLE_ID_MONIT`.
Так обновление уходит в конкретную заявку, а не всегда в №1.

### Жизненный цикл

- `ORACLE_EVENT=created` (по умолчанию) — первичная запись при создании локального тикета.
- `ORACLE_EVENT=closed` — первичная запись при закрытии.
- После успешной первичной записи событие `updated` снова вызывает функцию
  с `P_ID_MONIT` = номер заявки (Oracle `external_ref` или локальный `T-…`),
  чтобы обновление ушло в ту же заявку ServiceDesk.
- Антицикл: снимок тикета не включает комментарии SAYMON; повторный UPDATE
  с тем же содержимым заявки (fingerprint `oracle_content_fp`) не вызывает
  функцию и не ставит новый комментарий в аварию.
- Повторная *первичная* регистрация блокируется отметкой
  `external_meta.oracle_recorded`. Автоматического повтора при ошибке первичной
  отправки нет: перед ручной повторной отправкой нужна сверка с DBA.
- Комментарии в авариях SAYMON пишутся при каждой отправке (CREATE/UPDATE)
  и при CLOSE локального тикета (номер заявки, изменения группы).

Пустые `ORACLE_NAME_EQUIP` / `ORACLE_NAME_DEFECT` заполняются заголовком и
описанием группы аварий. Даты по умолчанию берутся из локального тикета
и приводятся к `ORACLE_TIMEZONE` (по умолчанию `Europe/Moscow`).
Фиксированные `ORACLE_B_DATE` / `ORACLE_E_DATE` задаются в формате
`DD.MM.YYYY HH:MM`.

Строки читаются из возвращённого `SYS_REFCURSOR`. Одна колонка сохраняется как
номер заявки. Для нескольких колонок укажите `ORACLE_RESULT_ID_COLUMN`; без неё
непустой курсор подтверждает выполнение, но номер не сохраняется.

### Подтверждение и откат

Бюджет ожидания задаётся `ORACLE_CONNECT_TIMEOUT_SEC` и `ORACLE_CALL_TIMEOUT_MS`.
Таймаут вызова уменьшается на уже затраченное время. Любая ошибка execute/fetch/
commit приводит к `rollback`. Сообщение `Oracle confirmed` появляется только
после успешного commit.

При сбое на этапе инициализации или подключения запускается диагностика
(режим драйвера, DNS, TCP). Она не повторяет авторизацию и не вызывает
хранимую функцию. Режимы `thin` и `thick` фиксируются на процесс: смена
`ORACLE_MODE` требует пересоздания контейнера. Комплект linux/amd64 по
умолчанию — Thick с Instant Client; `thin` нужен только если verifier
совместим с python-oracledb Thin.

Проверка без создания заявки:

```bash
python -m alarm_manager_server.plugins.oracle_check
```

### Комментарии в SAYMON

По умолчанию комментарий в аварию ставится в очередь **только после
подтверждённого commit**. Таймаут и ошибка вызова остаются в логах worker,
в историю аварии не пишутся. Отключить комментарии об успехе:
`ORACLE_SAYMON_COMMENT_ENABLED=false`.
Недоставленные комментарии повторяются независимо от новых событий тикета.
После первой регистрации событие UPDATE снова вызывает функцию Oracle
(с `P_ID_MONIT` = номер заявки); CLOSE локального тикета пишет комментарий
без повторного вызова (если первичная запись была на `created`).
Успешная отправка дополнительно пишется в stdout worker
(`Oracle ServiceDesk: отправка подтверждена`).

Подробности поставки, таймаутов и приёмки — в
[установке в закрытом контуре](offline-install.md).

## 2. Zammad

Плагин `ZammadTicketHandler` работает через REST API `/api/v1`.
Авторизация — токен пользователя с правом `ticket.agent`
(`Authorization: Token token=...`).

Включается, когда заданы URL, API-токен, клиент (`ZAMMAD_CUSTOMER`)
и группа: имя `ZAMMAD_GROUP` или числовой `ZAMMAD_GROUP_ID`.

| Событие | Действие |
|---|---|
| CREATE | Создаёт тикет с первой статьёй (note). Сохраняет внутренний `id` и публичный `number` (`#10042`) |
| UPDATE | Добавляет статью в существующий тикет. Если `ticket_id` ещё нет — создаёт тикет |
| CLOSE | Ставит `ZAMMAD_STATE_CLOSED` и добавляет статью о закрытии |

В Zammad публичный номер и внутренний `id` — разные поля. Повторные
обращения используют `external_meta.ticket_id`, а не номер из
`external_ref`.

Дополнительно:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `ZAMMAD_PRIORITY` | Приоритет тикета | `2 normal` |
| `ZAMMAD_STATE_OPEN` | Состояние при создании | `new` |
| `ZAMMAD_STATE_CLOSED` | Состояние при закрытии | `closed` |
| `ZAMMAD_ARTICLE_INTERNAL` | Внутренняя заметка (`true`) или видимая клиенту | `true` |

После успешного CREATE с внешним номером worker по умолчанию пишет
комментарий в историю инцидента SAYMON
(`TICKET_SAYMON_COMMENT_ENABLED`, общий для REST-плагинов).

## 3. Ранее добавленные плагины

Плагины ниже уже были в реестре до Oracle и Zammad. Каждый включается
своими переменными `.env` и обрабатывает CREATE / UPDATE / CLOSE.

- **Jira** — задача в проекте; комментарий при обновлении; опциональный transition при закрытии.
- **Redmine** — issue в проекте; journal notes при обновлении и закрытии; опциональная смена статуса.
- **Freshdesk** — тикет; приватная заметка при обновлении и закрытии.
- **ServiceNow** — запись Table API (`incident`); work notes при обновлении и закрытии.
- **SimpleOne** — запись Table API (`itsm_incident`); work notes при обновлении и закрытии.
- **Naumen / ITSM 365** — service call; комментарий при обновлении; смена состояния при закрытии.
- **ELMA365** — элемент приложения Public API; сообщение в ленту при обновлении и закрытии.
- **Bitrix24** — задача через входящий webhook; комментарий при обновлении; завершение при закрытии.
- **HP Service Manager / Service Desk** — инцидент REST API; journal при обновлении и закрытии.
